# Асинхронность, фоновые процессы и нагрузочный профиль сервиса

Документ описывает текущее поведение `microservice/` по исходному коду. Под
«асинхронно» ниже понимается неблокирующее ожидание сетевого I/O через `async/await`.
Это не означает, что задача автоматически выполняется в фоне или через очередь.

## 1. Что работает асинхронно

FastAPI-маршруты объявлены через `async def`, поэтому один процесс Uvicorn может
обслуживать другие запросы, пока текущий запрос ожидает внешний HTTP-сервис.

Асинхронно выполняются:

- запросы к Dify Chat/Chatflow API;
- запросы к Dify Dataset API;
- запросы к OpenRouter/OpenAI-compatible API;
- отправка сообщений, callback-ответов и файлов в MAX;
- получение обновлений MAX в режиме long polling;
- скачивание Excel по `file_url`;
- запросы к Ory Kratos;
- чтение загруженного тела запроса через FastAPI `UploadFile`;
- сетевое получение и загрузка файлов для сценариев распознавания документов.

Для внешних HTTP-запросов используется `httpx.AsyncClient`. Пока код ожидает
ответ Dify, MAX, OpenRouter или Kratos, event loop может переключиться на другой
готовый запрос.

Однако следующие операции остаются синхронными, даже когда вызываются из
`async def`:

- все операции SQLite через стандартный `sqlite3`;
- чтение и разбор Excel через `openpyxl`;
- разбор импортируемых карточек УСВО;
- чтение локальных файлов;
- построение XLSX/DOCX;
- работа с ZIP/XML при заполнении DOCX-шаблонов;
- расчёт агрегатов, фильтрация и построение полного контекста карточек;
- вычисление хэша всего набора карточек для проверки актуальности базы знаний.

Эти операции выполняются непосредственно в event loop, без `asyncio.to_thread`,
thread pool или отдельного worker-а. Крупный Excel, массовый экспорт, большой
DOCX или обход большого числа карточек может временно задержать другие запросы
в том же процессе Uvicorn.

## 2. Что выполняется в фоне

### 2.1. MAX long polling

Если в `config.yaml` установлено:

```yaml
max:
  polling: true
```

при старте FastAPI создаётся фоновая задача:

```python
asyncio.create_task(poll_loop(...))
```

Цикл постоянно вызывает MAX `GET /updates` с long-poll timeout 30 секунд.
Полученные обновления обрабатываются последовательно:

1. получается пакет `updates`;
2. первый update полностью проходит `bot.handle_update`;
3. затем начинается следующий update;
4. после обработки пакета выполняется следующий long-poll запрос.

Один медленный LLM-вызов, распознавание фото или отправка файла задерживает все
следующие события этого polling-цикла. При исключении цикл ждёт 3 секунды и
повторяет запрос.

Long polling и webhook нельзя использовать одновременно. Кроме того,
`max.polling: true` нельзя без дополнительной координации запускать с несколькими
Uvicorn workers: lifespan каждого worker-а создаст собственный polling-цикл.

### 2.2. Best-effort уведомления в MAX

После решения по заявлению веб-кабинет может запланировать отправку уведомления
в MAX через `loop.create_task(...)`. HTTP-ответ кабинету не ждёт завершения
отправки.

У этой фоновой задачи нет:

- постоянного хранилища;
- повторных попыток на уровне приложения;
- контроля результата вызывающим запросом;
- восстановления после перезапуска процесса;
- реестра незавершённых задач.

Если процесс завершится или MAX вернёт ошибку, уведомление может быть потеряно.

### 2.3. Что не является фоновым

Следующие тяжёлые действия выполняются внутри исходного HTTP-запроса или
обработки MAX update, и вызывающая сторона ждёт их завершения:

- обработка `/max/webhook`;
- ответ MAX-бота через Dify;
- распознавание фотографий;
- подбор меры поддержки;
- генерация и отправка DOCX;
- чат с ИИ в веб-кабинете;
- нормализация истории при импорте карточек;
- синхронизация карточек и мер с Dify Dataset;
- полная пересборка базы знаний УСВО;
- импорт и экспорт Excel.

Комментарий в webhook говорит о быстром возврате `200`, но фактически маршрут
выполняет `await bot.handle_update(update)` и отвечает только после всей
обработки update.

## 3. Как выполняются запросы к LLM

Все LLM-запросы выполняются в режиме ожидания результата. Для Dify используется:

```json
{
  "response_mode": "blocking"
}
```

Streaming в микросервисе не используется. HTTP-запрос остаётся открытым, пока
Dify или другой провайдер не вернёт полный ответ либо не сработает timeout.

### 3.1. Обычный вопрос MAX-боту

Последовательность:

1. сообщение и счётчик записываются в SQLite;
2. выполняется один blocking-запрос к MAX-ветке Dify;
3. Dify возвращает JSON с ответом, уверенностью и тематической оценкой;
4. при низкой уверенности создаётся эскалация оператору;
5. иначе ответ отправляется пользователю через MAX;
6. дополнительные проверки и предложения также могут вызвать внешние запросы.

Webhook или polling ждёт завершения этой последовательности.

### 3.2. Фото документов и меры поддержки

Один пользовательский сценарий может содержать несколько последовательных
LLM-вызовов:

1. vision-модель читает фотографии;
2. отдельный ассистент подбирает меру поддержки;
3. после сбора документов vision-модель извлекает поля;
4. при пропущенных полях LLM может переводить технические названия полей;
5. для старого сценария заявления отдельный Dify-ассистент генерирует DOCX;
6. затем файл загружается и отправляется через MAX API.

Для управляемых мер поддержки итоговый DOCX заполняется локально по шаблону, но
распознавание полей остаётся внешним LLM-вызовом.

### 3.3. Чат с ИИ в веб-кабинете

Перед основным ответом сервис:

1. загружает историю чата из SQLite;
2. получает и обходит текущие карточки УСВО;
3. вычисляет мета-информацию;
4. в обычном режиме проверяет хэш базы знаний;
5. если хэш изменился, прямо в запросе запускает полную пересборку Dataset;
6. при наличии planner-приложения может сначала вызвать отдельный LLM-планировщик;
7. затем вызывает основной Dify Chat/Chatflow;
8. сохраняет готовый ответ в SQLite.

Таким образом, один запрос чата может породить два LLM-вызова, а при устаревшей
базе знаний — ещё множество последовательных Dataset API-запросов.

В режиме `full_context` база знаний не пересобирается, но сервис формирует большой
prompt со всеми карточками в пределах `full_context_max_chars`. Это повышает
расход памяти, объём передаваемых данных, число токенов и время ответа LLM.

### 3.4. Импорт карточек УСВО

Для каждой импортируемой карточки отдельно вызывается нормализация истории.
Карточки обрабатываются последовательно. После сохранения выполняется
синхронизация с Dify Dataset:

- обычный импорт — по каждой новой карточке плюс мета-документ;
- импорт с `replace=true` — полная пересборка всей базы знаний.

Большой импорт может создать сотни последовательных внешних запросов и держать
один HTTP-запрос открытым длительное время.

### 3.5. Таймауты

Основные значения:

| Операция | Таймаут |
|---|---:|
| MAX API | 15 секунд по умолчанию |
| MAX long polling | 30 секунд ожидания update + таймаут клиента, обычно около 45 секунд |
| Dify MAX-ветка | 60 секунд по умолчанию |
| Web AI | 60 секунд |
| Dify/OpenRouter для документов | 90 секунд |
| Чат УСВО и его Dataset API | 90 секунд из текущего конфига |
| Скачивание Excel по `file_url` | 30 секунд |
| Ory Kratos | 20 секунд |
| Ожидание блокировки SQLite | до 10 секунд |

Таймаут одного этапа не является общим таймаутом всего сценария. Если сценарий
выполняет несколько последовательных запросов, итоговое время может быть суммой
их таймаутов и локальной обработки.

## 4. Какие очереди есть

### 4.1. Очередей задач в приложении нет

В проекте нет Celery, RQ, Dramatiq, Kafka, RabbitMQ, Redis Streams,
`asyncio.Queue` или другого broker/worker-механизма.

Нет отдельных очередей для:

- входящих MAX updates;
- LLM-запросов;
- распознавания документов;
- генерации DOCX;
- импорта Excel;
- синхронизации Dify Dataset;
- отправки уведомлений;
- повторной обработки ошибок.

Нет application-level rate limiter, общего семафора на LLM, ограничения числа
одновременных тяжёлых запросов и механизма backpressure.

### 4.2. Что похоже на очередь, но ею не является

- `updates` в ответе MAX long polling — временный пакет событий. Внутри процесса
  он обрабатывается последовательно, но это не собственная надёжная очередь
  сервиса.
- Таблицы `questions`, `escalations`, `applications` и `ai_chat_messages` —
  бизнес-состояние, а не очередь фоновых заданий.
- SQLite WAL улучшает совместную работу читателей и писателя, но не заменяет
  очередь и не сериализует бизнес-задачи.
- `asyncio.create_task` для уведомления MAX — задача в памяти одного процесса,
  без гарантии доставки.

При перегрузке запросы будут ждать в сетевом стеке Uvicorn/reverse proxy,
внутри внешних Dify/MAX-сервисов или конкурировать за event loop и SQLite.
Приложение не контролирует длину такого ожидания и не сообщает размер backlog.

## 5. Что нагружает сервер

### CPU

- разбор больших XLSX через `openpyxl`;
- импорт и нормализация большого количества карточек;
- фильтрация и агрегация по всем карточкам;
- вычисление SHA-256 по сериализованному полному набору карточек;
- формирование full-context prompt;
- создание XLSX/DOCX;
- ZIP/XML-обработка DOCX-шаблонов;
- сериализация больших JSON и текстовых контекстов;
- linkify ФИО по большому списку карточек.

### Оперативная память

- `await file.read()` загружает файл целиком в память;
- `request.body()` загружает raw body целиком;
- скачанный по `file_url` файл хранится как `resp.content`;
- Excel и DOCX передаются и возвращаются как массивы байтов;
- импорт сначала создаёт список всех карточек;
- экспорт строит готовый файл в памяти;
- full-context собирает большой текст всех карточек;
- большие ответы и история чата одновременно существуют в нескольких строковых
  представлениях.

В коде приложения не видно общего ограничения размера upload/body или количества
фотографий. Фактические ограничения могут быть только у reverse proxy.

### Диск и SQLite

- каждое действие открывает новое синхронное соединение SQLite;
- вопросы, сообщения чата, эскалации, заявки и карточки создают записи;
- при большом числе одновременных записей остаётся один SQLite writer;
- конкурентные записи могут ждать до 10 секунд и завершаться `database is locked`;
- WAL-файл может быстро расти при интенсивной записи и долгих читателях;
- массовый импорт выполняет много отдельных транзакций, а не одну пакетную;
- шаблоны и основная Excel-таблица читаются с локального диска.

### Сеть и внешние сервисы

- Dify LLM и Dataset API;
- OpenRouter/OpenAI-compatible API;
- MAX API;
- Ory Kratos;
- произвольные `file_url`;
- скачивание и повторная загрузка документов.

Во многих сценариях именно внешний сервис будет первым ограничением. При этом
открытые HTTP-запросы продолжают занимать соединения Uvicorn и reverse proxy.

## 6. Рекомендуемые сценарии нагрузочного тестирования

Тестировать следует отдельно локальную производительность микросервиса и
производительность полного контура с настоящими Dify/MAX. Подмена внешних
клиентов нужна для измерения CPU/SQLite, реальные интеграции — для измерения
общей задержки и отказоустойчивости.

### 6.1. Базовые HTTP-сценарии

| Сценарий | Что измерять |
|---|---|
| Частые `GET /api/web/*` | RPS, p95/p99, влияние SQLite и чтения Excel |
| Параллельный login | отсутствие rate limit, CPU хеширования пароля, блокировки БД |
| `/excel/extract` с файлами разных размеров | CPU, память, задержка event loop |
| Одновременные импорты УСВО | память, SQLite locks, дубли, время синхронизации Dify |
| Одновременные экспорты | CPU, память, размер ответа |
| Массовые сообщения `/api/web/ai-chats/{id}/messages` | число LLM-запросов, timeout, p95/p99 |
| Ручная пересборка `/api/web/ai-knowledge/usvo/rebuild` | длительность, число Dataset-запросов, поведение при параллельном запуске |
| Массовый CRUD мер поддержки | задержка из-за синхронной Dataset-синхронизации |

### 6.2. MAX webhook

Профиль:

- короткие текстовые сообщения;
- сообщения, приводящие к эскалации;
- медленные ответы Dify;
- ошибки и timeout Dify;
- повтор одного и того же update;
- параллельные сообщения одного пользователя;
- параллельные сообщения разных пользователей;
- фото и документы большого размера;
- callback во время незавершённой обработки предыдущего сообщения.

Проверять:

- сколько времени webhook держит соединение;
- начинает ли MAX повторно доставлять update;
- появляются ли дубли вопросов, заявок и эскалаций;
- нарушается ли порядок состояний пользователя;
- не теряются ли ответы после исключений;
- как меняется throughput при одном и нескольких Uvicorn workers.

### 6.3. MAX long polling

Проверить большой пакет updates, в котором первый update искусственно задержан
на 60–90 секунд. Ожидаемое текущее поведение: все следующие updates ждут его
завершения.

Отдельно проверить:

- восстановление после сетевой ошибки и паузу 3 секунды;
- перезапуск процесса во время обработки;
- запуск двух polling-процессов;
- ошибочную конфигурацию polling вместе с webhook;
- `max.polling: true` вместе с `--workers 2` и более.

### 6.4. База знаний УСВО

Профилировать наборы 100, 500, 1 500 и более карточек:

- расчёт signature;
- полный rebuild;
- одновременный rebuild из двух запросов;
- первый AI-запрос после изменения Excel;
- импорт с `replace=true`;
- удаление карточки, запускающее полный rebuild;
- отказ Dify на середине пересборки;
- timeout и повторный запуск после частично созданных документов.

Нужно фиксировать количество HTTP-запросов к Dataset API, общее время, число
дубликатов и фактическое состояние Dataset после ошибки.

### 6.5. Длительный soak-тест

В течение нескольких часов смешивать:

- чтение веб-кабинета;
- вопросы MAX и AI-чата;
- создание и изменение заявок;
- импорты/экспорты;
- периодические ошибки внешних сервисов.

Контролировать:

- память процесса;
- число открытых соединений;
- размер SQLite, `-wal` и `-shm`;
- частоту `database is locked`;
- незавершённые HTTP-запросы;
- потерянные фоновые уведомления;
- рост времени ответа p95/p99.

## 7. Уязвимые места для тестирования

Ниже перечислены места, которые стоит проверять в первую очередь в разрешённом
тестовом контуре.

1. **Нет backpressure и лимита параллельных LLM-запросов.** Всплеск запросов
   напрямую превращается во всплеск соединений к Dify/OpenRouter и может исчерпать
   лимиты внешнего API, reverse proxy или файловые дескрипторы.

2. **Webhook ждёт полную обработку.** Медленный LLM повышает вероятность timeout
   со стороны MAX/proxy и повторной доставки одного update.

3. **Нет идемпотентности входящих MAX updates.** В коде не видно хранения
   обработанного update/message ID до начала бизнес-операции. Повтор может
   продублировать вопрос, эскалацию, сообщение или переход состояния.

4. **Long polling последовательный.** Один тяжёлый update блокирует весь backlog.

5. **Несколько workers с polling.** Каждый worker запускает собственный цикл,
   что может привести к конкурирующему получению и обработке событий.

6. **Синхронный SQLite внутри async-маршрутов.** Под конкурентной записью
   возможны задержки event loop и `database is locked`.

7. **Состояние диалога не защищено транзакцией или lock-ом на пользователя.**
   Два сообщения или callback-а одного пользователя могут одновременно прочитать
   старое состояние и записать конфликтующие переходы.

8. **Полная пересборка базы знаний не имеет mutex.** Несколько запросов могут
   одновременно удалить и заново создавать одни и те же документы.

9. **Автопересборка выполняется внутри AI-запроса.** Первый пользователь после
   изменения источника может получить очень большую задержку или timeout.

10. **Dataset-синхронизация последовательная.** Большое число карточек или мер
    создаёт длинную цепочку внешних запросов без resumable job и checkpoint.

11. **Частичный rebuild.** При отказе Dify база знаний может остаться частично
    удалённой или частично заполненной. Нужна проверка восстановления и отсутствия
    дублей.

12. **Импорт карточек выполняет LLM-нормализацию по одной записи.** Большой файл
    может держать запрос минуты и создавать высокую стоимость внешних вызовов.

13. **Нет явных лимитов размера файлов и request body в приложении.** Большие
    Excel, DOCX, фотографии и raw body могут вызвать скачок памяти или CPU.

14. **`file_url` скачивается сервером.** Следует проверить SSRF-защиту:
    localhost, loopback, внутренние IP, cloud metadata, редиректы, DNS rebinding,
    большие и бесконечные ответы. В текущем маршруте видимой фильтрации адресов и
    лимита скачиваемого размера нет.

15. **Webhook не показывает проверку подписи/секрета MAX.** Следует проверить,
    может ли посторонний клиент отправить поддельный update напрямую на
    `/max/webhook`.

16. **Нет rate limit на login, AI и тяжёлые admin-операции.** Проверить brute
    force, расход внешних LLM-квот и доступность сервиса при частых rebuild/import.

17. **Фоновые уведомления MAX недолговечны.** Перезапуск сразу после ответа API
    может потерять отправку без возможности повтора.

18. **Новые `httpx.AsyncClient` создаются на каждый запрос.** Под нагрузкой нет
    общего connection pool между вызовами; нужно измерить число TCP/TLS
    соединений, TIME_WAIT и стоимость handshake.

19. **Суммарный timeout сценария не ограничен.** Цепочка из нескольких шагов по
    60–90 секунд может жить значительно дольше допустимого timeout reverse proxy.

20. **Логи и наблюдаемость ограничены.** Нет метрик длины backlog, количества
    активных LLM-запросов, времени SQLite-lock, размера очереди, числа retries и
    потерянных background tasks. Нагрузочный тест должен собирать эти показатели
    внешними средствами.

## 8. Минимальный набор метрик

Для каждого сценария следует собирать:

- RPS и число одновременно выполняемых запросов;
- p50, p95, p99 и максимальную задержку;
- HTTP-коды и типы исключений;
- timeout по каждому внешнему провайдеру;
- число активных соединений и TIME_WAIT;
- CPU, RSS и доступную память;
- event-loop lag;
- длительность и частоту SQLite write locks;
- размер `state.db`, `state.db-wal`, `state.db-shm`;
- число LLM/Dataset/MAX вызовов на один пользовательский запрос;
- стоимость/токены LLM;
- число повторных MAX updates и бизнес-дублей;
- количество потерянных или незавершённых уведомлений;
- состояние базы знаний до и после частичного отказа.

Главный риск текущей архитектуры — не максимальная скорость отдельной операции,
а отсутствие контролируемой очереди и ограничения конкурентности. При всплеске
нагрузки тяжёлые задачи выполняются непосредственно в HTTP/webhook/polling
контексте, конкурируют за event loop, SQLite и внешние API и не имеют надёжного
механизма отложенного повтора.
