# Как работают ответы по карточкам УСВО (поиск и «Чат с ИИ»)

Документ описывает, как микросервис отвечает на вопросы по карточкам УСВО в разделе
веб-кабинета **«Чат с ИИ»**: что отправляется в модель, как обходится лимит модели в
32k токенов и как устроен **детерминированный движок запросов**.

> Коротко: на 1500 карточек нельзя «затолкать всё» в контекст модели (32k токенов). Поэтому
> ответ собирается из трёх источников — **точный детерминированный расчёт по всей базе**,
> **семантический поиск (RAG)** и **предрассчитанная мета-сводка**. Вопросы-перечисления и
> подсчёты считаются в Python по всем карточкам (точно), а смысловой поиск конкретных людей —
> через базу знаний Dify.

---

## 1. Общая картина

```
Пользователь → веб-кабинет «Чат с ИИ»
      │
      ▼
AiChatService.send_message  (microservice/app/web/ai_chat.py)
      │  собирает запрос (query) из нескольких блоков:
      │   1) текущий вопрос + история диалога + формат ответа
      │   2) МЕТА-сводка по всей базе (числа/разбивки)            ← всегда
      │   3) «Точные данные по всей базе» (детерминированный блок) ← если вопрос про выборку/счёт
      ▼
Dify-приложение usvo_chat_assistant.yml
      │   knowledge-retrieval (RAG, top_k=12) по датасету карточек ← семантический поиск
      │   LLM qwen3-32b-fp8-v2 формирует ответ по всем блокам
      ▼
Ответ → linkify_usvo_names (ФИО → ссылки) → кабинет
```

Три механизма дополняют друг друга:

| Тип вопроса | Кто отвечает | Точность |
|---|---|---|
| «Сколько …», «перечисли всех с …», «распределение по …» | **детерминированный движок** (Python по всем карточкам) | точно, по всей базе |
| «Расскажи про Иванова», «кто упоминал протезирование» | **RAG** (top-k чанков из базы знаний) | по релевантным карточкам |
| Общая статистика как фон | **мета-сводка** (предрасчёт) | точно, агрегаты |

Все три приходят в модель уже **внутри одного запроса** (`query`), отдельные блоки помечены
заголовками. В системном промпте задано правило: **блок «Точные данные по всей базе» —
авторитетный** для списков и чисел; RAG-контекст — лишь дополнение по конкретным людям.

---

## 2. Почему так: ограничение 32k токенов

Модель `qwen3-32b-fp8-v2` принимает на вход ~32k токенов. Одна карточка ≈ 500–1000 токенов,
1500 карточек ≈ 1 млн+ токенов — это физически не помещается в контекст.

- **RAG** возвращает только top-k наиболее похожих чанков (сейчас `top_k=12`), поэтому
  отлично ищет «конкретного человека / похожую ситуацию», но **не может** дать исчерпывающий
  список или точный счёт по всей базе («перечисли ВСЕХ с орденом Мужества», «СКОЛЬКО в
  посёлке X нуждаются в работе») — большинство карточек просто не попадёт в выдачу.
- **Детерминированный движок** решает именно эту проблему: микросервис держит **все**
  карточки в памяти (`records_provider()`), считает ответ точно в Python и отдаёт модели
  компактный готовый результат (имена + ключевые поля, или числа), который **влезает** в 32k.

## 3. Детерминированный движок запросов

Модуль: [microservice/app/web/usvo_query.py](microservice/app/web/usvo_query.py).

Поток: **`plan_query` → `execute_query` → `format_result`** (обёртка `build_query_context`).

### 3.1. План запроса — `plan_query` (вопрос → `QuerySpec`)

Вопрос на естественном языке превращается в структуру `QuerySpec` (намерение + фильтры).
Два режима:

1. **Через Dify-планировщик** (если задан `dify.usvo_ai.planner_app_key`) — ассистент
   [usvo_query_assistant.yml](usvo_query_assistant.yml) со `structured_output` возвращает
   `QuerySpec` в виде строгого JSON. Базы знаний планировщику не нужно — это только разбор
   формулировки.
2. **Офлайн-эвристика** `plan_offline` (если ключ не задан или Dify недоступен/вернул не-JSON) —
   разбор по ключевым словам. Работает без сети, поэтому ответы по выборкам работают всегда.

`QuerySpec` (основные поля):

| Поле | Значение |
|---|---|
| `intent` | `count` (сколько), `list` (перечислить), `aggregate` (разбивка), `lookup` (конкретный человек), `semantic` (смысловой вопрос → отдаём в RAG, движок молчит) |
| `status` | подстрока статуса (напр. «демобилизован») |
| `locality` | населённый пункт (из адреса) |
| `awards_contains` | подстрока награды (напр. «мужеств», «отваг») |
| `gender` | `м` / `ж` |
| `disability` | `yes` / `no` |
| `age_min`, `age_max` | возрастной диапазон |
| `flags` | подмножество `vbd`, `unemployed`, `stale_contact`, `support_need`, `org`, `awards`, `directive` |
| `field_label` / `field_value` | поиск по произвольному полю карточки |
| `name_query` | подстрока ФИО |
| `sort` | `age_desc` / `age_asc` / `name` |
| `limit` | ограничение количества (напр. «топ-5») |
| `aggregate_by` | для `aggregate`: `status`/`locality`/`gender`/`age`/`disability`/`awards` |

Как офлайн-эвристика определяет намерение:
- слова `сколько`, `количество`, `число` → `count`;
- `перечисли`, `список`, `покажи всех`, `назови всех` → `list`;
- `распределение`, `разбивка`, `статистика`, `по статусам/возрасту/полу` → `aggregate`;
- иначе `semantic`; **но** если в вопросе есть фильтр **и** вопросительный маркер
  (`кто`, `у кого`, `какие`, `назови`, `выведи`, `покажи`, `перечисл…`) → повышается до `list`.
  Поэтому «расскажи про меры поддержки семьям» остаётся `semantic` (информационный вопрос и
  уходит в RAG), а «**кто** в посёлке Развилка нуждается в работе» → `list` (точная выборка).

Награды распознаются только при «наградном» маркере (`орден`, `медаль`, `награда`, `отвага`,
`благодарность`, `отличие`) — чтобы «ветераны **боевых** действий» (это флаг `vbd`) не путать с
медалью «За **боевые** отличия».

### 3.2. Исполнение — `execute_query` (точно по всем карточкам)

`QuerySpec` применяется ко **всем** записям `records_provider()`. Предикаты фильтров —
зеркало логики веб-кабинета (`WebService._filtered_records`), плюс переиспользуются помощники
из [usvo_knowledge.py](microservice/app/web/usvo_knowledge.py): `_locality` (населённый пункт из
адреса), `_age` (возраст по дате рождения), `_field_value` (значение поля по подстроке метки),
`_yes` (да/нет). Флаги (`vbd`, `unemployed`, организации, награды, поручение Главы и т.д.)
берутся из `record.flags` / `compute_flags`.

Результат — `QueryResult`: отфильтрованный список, **полный total**, и (для `aggregate`)
разбивка-counter по выбранному измерению.

### 3.3. Формат для модели — `format_result` (с бюджетом)

Готовится компактный текстовый блок:
- строка с критериями выборки и **точным общим числом** («Всего подходящих карточек: N»);
- для `aggregate` — разбивка («Демобилизован: 3; Служит: 1» и т.п.);
- для `list`/`lookup` — строки `ФИО (карточка #id); статус; населённый пункт; награды`.

Действует **бюджет по объёму** (`DEFAULT_MAX_CHARS = 24000` символов ≈ заметно ниже 32k, чтобы
осталось место под систему/историю/RAG/ответ). Если список не помещается (например, 1500 имён),
он усекается, но в блоке прямо указывается **точное общее число** и помета «показано N из M» —
модель сообщает пользователю реальный счёт и предлагает уточнить фильтры. Сами числа и факт
полноты при этом не искажаются.

Если `intent == semantic`, движок возвращает пустую строку — вопрос целиком отрабатывает RAG.

## 4. Что попадает в модель (сборка запроса)

Метод [`AiChatService.send_message`](microservice/app/web/ai_chat.py):

1. `knowledge.ensure_current()` — при необходимости досинхронизирует карточки в базу знаний Dify.
2. `meta.text()` — мета-сводка (числа/разбивки по всей базе).
3. `build_query_context(question, records, meta, planner)` — детерминированный блок (или пусто).
4. `_prompt(...)` склеивает: вопрос → формат ответа → история → мета → **«Точные данные по всей
   базе»** → системная инструкция → инструкция формата.
5. `dify.ask_text(prompt)` → ответ от `usvo_chat_assistant.yml`.
6. `linkify_usvo_names(answer, records)` → ФИО становятся ссылками (см. §6).

## 5. Карточки в базе знаний Dify (для RAG) и чанкинг

Карточки кладёт в датасет `dify.usvo_ai.dataset` сервис
[`UsvoCardKnowledgeSyncService`](microservice/app/web/usvo_knowledge.py): **по одному документу на
карточку** «Карточка УСВО #<id>: <ФИО>» (текст готовит `build_card_chunk`) + отдельный документ
«Мета-информация УСВО». Синхронизация идёт автоматически (по контрольной сумме всех карточек).

**Важно про дробление на чанки.** Раньше документы загружались с `process_rule: automatic`, а у
Dify «automatic» = разделитель `\n\n` и **максимум 500 токенов на чанк**, из-за чего карточка
резалась на куски. Теперь правила заданы явно в
[dify_client.py](microservice/app/max/dify_client.py):

- `DEFAULT_PROCESS_RULE` — для всех загрузок в базу знаний: разделитель `\n\n`, **до 4000
  токенов** на чанк (ответы операторов, меры поддержки, ручная загрузка файлов/текста).
- `SINGLE_CHUNK_PROCESS_RULE` — для **карточек УСВО**: разделитель-сентинел, которого нет в
  тексте, поэтому **карточка не дробится — один документ = один чанк** (≤4000 токенов как
  предохранитель). Это даёт цельный контекст по человеку при RAG-поиске.

Предобработка (`remove_extra_spaces`, `remove_urls_emails`) выключена намеренно: чтобы не ломать
форматирование карточки и **не вырезать ссылку** `/usvo/cards/<id>` из текста.

## 6. ФИО → ссылка на карточку

После ответа модели [`linkify_usvo_names`](microservice/app/web/ai_chat.py) находит в тексте
**однозначные полные ФИО** (имя встречается в базе ровно один раз, ≥2 слов) и оборачивает их в
markdown-ссылку `[ФИО](/usvo/cards/<id>)`, не трогая уже готовые ссылки. На фронтенде
`renderAiText`/`bindAiPersonLinks` (`static/app.js`) превращают их в кликабельные ссылки,
открывающие карточку. Поэтому детерминированный блок и системный промпт требуют писать **полное
ФИО** — иначе ссылка не построится.

## 7. Настройка

В `config.yaml`, блок `dify.usvo_ai`:

```yaml
dify:
  usvo_ai:
    app_key: "app-..."          # usvo_chat_assistant.yml — сам чат (обязательно для онлайн-ответов)
    planner_app_key: "app-..."  # usvo_query_assistant.yml — планировщик (необязательно; пусто → офлайн-разбор)
    dataset:
      api_key: "dataset-..."    # Knowledge API: куда синхронизируются карточки и откуда идёт RAG
      dataset_id: "..."
```

Степени готовности:
- **Ничего не настроено** — чат не отвечает онлайн, но детерминированный движок и так считает
  выборки/числа точно (офлайн-разбор вопроса).
- **`app_key` + `dataset`** — полноценный чат: детерминированные выборки + RAG + мета.
- **+ `planner_app_key`** — разбор вопроса делает LLM (надёжнее на сложных формулировках);
  без него работает офлайн-эвристика.
