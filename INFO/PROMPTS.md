# PROMPTS.md — промты для ИИ сценария «оформление меры поддержки по фото»

Сценарий в MAX-боте (задание 2):

```
Пользователь шлёт фото документов
  → ① Визуальная модель (Dify workflow) распознаёт документы и предлагает меру
  → бот предлагает оформить меру  →  пользователь соглашается
  → ② Ассистент-заполнитель (Dify, отдельный app) раскладывает данные по полям заявления
  → микросервис собирает .docx  →  бот шлёт файл на подтверждение
  → пользователь подтверждает  →  заявление падает в админ-раздел «Заявления»
```

## Где формируется .docx?

Возможны два места — оба поддержаны:

1. **В Dify** (`document_assistant.yml`, основной путь) — цепочка
   `start (+ файл-шаблон) → LLM (structured output) → code (build_vars) →
   generate_docx (плагин scibox/document-generator) → answer`. Узел `generate_docx`
   берёт DOCX-шаблон `Zayavlenie_Shablon.docx` и подставляет в него `{{плейсхолдеры}}`.
   Микросервис (`doc_ai.generate_application_docx`) при `awaiting_confirm`:
   **загружает шаблон из `dify.doc_template_path` в Dify** (Files API → `template`
   узла Start), шлёт поля заявления (JSON), получает готовый файл из ответа
   (`message_files`) и скачивает его. **Куда класть новый шаблон:**
   `microservice/data/Zayavlenie_Shablon.docx` (путь задаётся `dify.doc_template_path`).

2. **В микросервисе** (`app/docs/forms.py::build_application_docx`, офлайн-фолбэк) —
   если `doc_fill_app_key` не настроен или Dify недоступен/не вернул файл, .docx
   собирается из тех же полей средствами `app/common/docx.py` (без сторонних
   библиотек). Этот же путь использует скачивание в админ-разделе «Заявления».

Иными словами: заполнение полей — это LLM (Dify или фолбэк), а сборка файла — либо
плагин document-generator в Dify, либо рендер в микросервисе. Схема полей у обоих общая
(`forms.normalize_application`).

Оба шага вызываются микросервисом (`app/docs/doc_ai.py`). Ключи приложений — в
`config.yaml`:

```yaml
dify:
  doc_vision_app_key: "app-..."   # шаг ①, визуальная модель
  doc_fill_app_key:   "app-..."   # шаг ②, ассистент-заполнитель (document_assistant.yml)
```

Если ключи не заданы (плейсхолдеры `app-xxxx`), микросервис использует
детерминированный офлайн-фолбэк — сценарий полностью демонстрируется без Dify.

Обе модели должны возвращать **строго JSON** (без пояснений и markdown-ограждений).
Схема одна и та же — `app/docs/forms.py::normalize_application` приводит её к виду,
который рендерится в заявление и показывается в админ-разделе.

## ① Промт для визуального Dify-workflow (`doc_vision_app_key`)

**Готовый экспорт — `vision_assistant.yml`** (импортируйте в Dify). Это advanced-chat
с включённым приёмом изображений (Features → Image upload), узлом LLM с `vision: enabled`
и JSON-схемой (structured output), и answer, возвращающим JSON. **Модель выберите свою**
в узле «Распознавание документов (VL)» — там стоит плейсхолдер `qwen3-vl-8b-instruct`.

> Важно про ключ и модель. Ошибка `401 key_model_access_denied … key can only access
> models=['…']` означает, что API-ключ приложения не имеет доступа к выбранной VL-модели.
> Нужен ключ/проект, которому разрешена мультимодальная (vision) модель — текстовая
> `qwen3-next-80b-…` фото не примет. Выберите VL-модель и ключ с доступом к ней.

# Сценарий «Меры поддержки» (управляемые администратором меры)

В отличие от жёстко зашитого ЖКУ-сценария выше, **меры поддержки заводит администратор**
в веб-кабинете (раздел «Заявления» → подраздел «Меры поддержки»): название, описание,
список требуемых документов, DOCX-шаблон с размеченными полями, активность. Бот MAX
показывает активные меры inline-кнопками («Оформление мер поддержки»), последовательно
собирает фото документов, распознаёт данные, заполняет шаблон и подаёт заявление. Меры
**не хардкодятся** — источник данных БД (`support_measures`) и база знаний.

## Формат разметки шаблона

Плейсхолдеры в загружаемом .docx — `{{snake_case}}`, например:
```
{{full_name}}  {{passport_series}}  {{passport_number}}  {{registration_address}}
{{military_office_certificate_date}}  {{bank_account}}  {{phone_number}}
```
Микросервис извлекает их автоматически при загрузке шаблона
(`app/docs/templates.py::extract_placeholders`), офлайн-заполнение —
`fill_template_docx` (stdlib, подстановка `{{key}}` → значение, со склейкой соседних
runs Word). Админ может поправить человекочитаемые подписи полей в форме меры.

## ③ Промт распознавания произвольных полей (визуальная модель)

**ПРЕДПОЧТИТЕЛЬНО — единый ассистент `documents_assistant.yml`** (см. ниже «Единый
ассистент документов»). Ветка `extract` принимает список полей меры во входе `fields`
(JSON `[{"key","label"}]`) и фото в `files`, возвращает СТРОГО JSON:
```json
{ "filled_fields": { "<ключ>": "<значение>" }, "missing_fields": ["<ключ>"] }
```
Чего не видно на фото — ключ попадает в `missing_fields` (не в `filled_fields`).

Легаси-путь (когда `documents_app_key` не задан): при `provider=openrouter` промт
строится в коде (`_build_fields_prompt`) из плейсхолдеров меры и уходит вместе с фото
прямо в OpenRouter; при `provider=dify` тот же промт уходит в `query` старого
`vision_assistant.yml` (его фиксированная ЖКУ-схема для произвольных полей не подходит —
ещё одна причина перейти на единый ассистент).

# Единый ассистент документов (`documents_assistant.yml`, `dify.documents_app_key`)

Один advanced-chat с **роутером по входу `task`** на 4 ветки — закрывает все документные
сценарии MAX-бота одним приложением и **заменяет прямые вызовы OpenRouter**:

| `task`      | вход                              | ветка / vision | выход (микросервис парсит)                     | метод `DocAI`          |
|-------------|-----------------------------------|----------------|------------------------------------------------|------------------------|
| `read`      | фото (`files`)                    | LLM + vision   | связный текст описания ситуации                | `read_documents_text`  |
| `extract`   | фото + `fields` (JSON списка)     | LLM + vision   | `{filled_fields, missing_fields}` (JSON)       | `extract_fields`       |
| `translate` | `fields` (JSON списка)            | LLM, без vision| `{ "<key>": "<рус. подпись>" }` (JSON)         | `translate_labels`     |
| `recognize` | фото (`files`), ветка по умолчанию| LLM + vision   | ЖКУ-JSON (structured_output, фикс. схема)      | `analyze_documents`    |

Микросервис (`app/docs/doc_ai.py::_ask_documents_dify`) шлёт `inputs={task, fields}` и
`files`, читает `answer`. Промты ветвей встроены в YAML. **VL-модель** выберите сами в
узлах `read`/`extract`/`recognize` (плейсхолдер `qwen3-vl-8b-instruct`); ветка `translate`
текстовая (`qwen3-32b-fp8-v2`). Достаточно импортировать ассистент, взять его API-ключ и
вписать в `dify.documents_app_key` — OpenRouter после этого не нужен.

## ④ Ассистент подбора меры (`measure_app_key`, measure_assistant.yml)

Для текстовых запросов «какая мера мне подойдёт» бот вызывает `DocAI.select_measure`.
Ассистент `measure_assistant.yml` (Start → knowledge-retrieval по базе знаний мер → LLM
со `structured_output` → answer) возвращает строго JSON:
```json
{ "measure_id": 12, "measure_title": "Единовременная выплата", "found": true, "confidence": 0.82 }
```
`found=false`, `measure_id=0` — подходящая мера не найдена. При незаполненном
`dify.measure_app_key` микросервис использует офлайн-подбор по ключевым словам
(`measures.match_measure_offline`).

**Автоматическое наполнение базы знаний.** Достаточно заполнить `dify.dataset.api_key`
и `dify.dataset.dataset_id` (тот же датасет, что для ответов на вопросы) — дальше каждая
активная мера автоматически попадает в базу знаний **отдельным документом**
«Мера поддержки #<id>: …» при создании/изменении/загрузке шаблона в кабинете
(`WebService.sync_measure_to_kb` → `DifyClient.upsert_document_text`, обновление на месте
без дублей; деактивация/удаление → `remove_measure_from_kb`). Кнопка «Синхронизировать
с ИИ» (`sync_measures_kb`) делает полную пересинхронизацию всех мер. Текст одного
документа формирует `measures.one_measure_text`.
